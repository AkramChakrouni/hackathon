# Encryption and Key Management Standard

**Document ID:** POL-SEC-003 | **Version:** 3.4 | **Owner:** Security | **Effective:** 1 June 2026

## 1. Scope

This standard defines the cryptographic controls that protect customer data and Kestrel secrets across the Kestrel Platform and corporate IT. It applies to all environments (production, staging, development) and all regions (eu-central-1, eu-west-1, us-east-1).

## 2. Encryption at rest

All customer data is encrypted at rest using AES-256 through AWS Key Management Service (KMS):

- **Per-tenant keys.** Each customer tenant is assigned a dedicated symmetric KMS customer master key at provisioning. Data belonging to that tenant in Amazon Aurora PostgreSQL, Amazon S3, and the analytics warehouse is encrypted under that tenant's key using envelope encryption. Data keys are generated by KMS, encrypted under the tenant key, and stored alongside the ciphertext.
- **Platform keys.** Shared infrastructure components (message queues, caches, logs, backups) use platform-level KMS keys, one per service and region.
- **Storage services.** EBS volumes, RDS/Aurora storage, S3 buckets, ElastiCache, and OpenSearch all have encryption enforced by AWS Config rules; unencrypted resources fail deployment and trigger an alert.
- **Backups.** Aurora snapshots and S3 backup copies are encrypted under the same tenant keys, and cross-region copies are re-encrypted with a replica key in eu-west-1.

Key material never leaves the AWS KMS hardware boundary; Kestrel staff cannot export or view key material.

## 3. Encryption in transit

- All public endpoints (application, API, webhooks, status page) enforce TLS 1.2 as a minimum, with TLS 1.3 preferred and negotiated by the vast majority of clients. TLS 1.0 and 1.1 are disabled; SSLv3 and RC4/3DES cipher suites are not offered.
- HSTS is set with a one-year max-age and preload; the domain is on the browser preload list.
- Internal service-to-service traffic within the VPC is encrypted with mutual TLS via the service mesh (AWS App Mesh with Envoy) using certificates issued by AWS Private CA and rotated every 24 hours.
- Connections to customer data sources (databases, SaaS APIs) use TLS with certificate validation; connectors refuse plaintext database connections unless the customer explicitly overrides this for a private-network source.
- Outbound email via Twilio SendGrid uses TLS; DKIM, SPF, and DMARC (p=reject) are configured.

Certificates for public endpoints are issued by Let's Encrypt via Cloudflare and rotated automatically every 60 days.

## 4. Key lifecycle

| Activity | Practice |
|---|---|
| Generation | KMS-generated, 256-bit symmetric; asymmetric keys (RSA-4096 or ECDSA P-256) for signing |
| Rotation | Annual automatic rotation for all KMS keys; previous key versions retained for decrypting existing data |
| Access | KMS key policies restrict use to specific IAM roles; no human role has `kms:Decrypt` on tenant keys |
| Monitoring | All KMS API calls logged to CloudTrail and Datadog; anomalous usage alerts to on-call |
| Revocation | Tenant key is scheduled for deletion 30 days after contract termination, following data deletion |
| Backup | Keys are AWS-managed with multi-Region replicas for DR; no Kestrel-held copies |

## 5. Secrets management

Application secrets, database credentials, API keys, and third-party tokens are stored in AWS Secrets Manager with automatic rotation for database credentials every 30 days. Secrets are injected at runtime through IAM-authenticated retrieval; they are never committed to source control (enforced by GitHub secret scanning with push protection) or written to logs (enforced by Datadog sensitive-data scanner rules). Developers use short-lived credentials from AWS IAM Identity Center; long-lived access keys are prohibited and detected by a daily audit.

## 6. Hashing and passwords

Local account passwords are hashed with Argon2id (memory 64 MiB, 3 iterations). API tokens are stored as SHA-256 hashes. Data integrity for exports is provided through SHA-256 checksums published alongside each export file.

## 7. Approved algorithms

Approved: AES-256-GCM, ChaCha20-Poly1305, RSA-2048 minimum (4096 for signing), ECDSA P-256/P-384, SHA-256/384, HMAC-SHA256, Argon2id. Prohibited: MD5, SHA-1 (except for legacy git object identifiers), DES/3DES, RC4, RSA below 2048 bits.

## 8. Compliance mapping

This standard satisfies ISO/IEC 27001:2022 controls A.8.24 (use of cryptography) and A.8.20 (network security), and SOC 2 criteria CC6.1, CC6.6, and CC6.7, all tested without exception in the FY2025 report.
